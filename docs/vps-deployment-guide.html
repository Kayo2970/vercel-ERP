Deploying LEADS Dashboard on a Fresh VPS

leadsnextgencentre.online · reformatted VPS, root install, everything lives at /ERP

Steps

  1. What's already in place
  2. SSH in as root and run the setup script
  3. Confirm it's live
  4. Enable HTTPS (if you didn't set an email in the script)
  5. First login & re-configuring email
  6. Redeploying updates later
  7. Backups
  8. Troubleshooting cheat-sheet
1

What's already in place

Since this is the same VPS being reformatted (not a new box), most of the usual first-VPS setup doesn't apply here:

  • DNS is already correct. The leadsnextgencentre.online records are still sitting at Hostinger pointing at this VPS's IP — nothing to touch there unless the reformat also changed the IP.
  • No separate deploy user. Everything runs as root — simpler, and fine for a single-admin box like this.
  • Fixed install path. The app always lives at /ERP (with the Next.js app itself in /ERP/leads-dashboard).
One thing genuinely does not survive the reformat: the SMTP/DKIM configuration you set up in the dashboard's Email Management screen. That lived in the app's own database on the old disk, not in DNS — Step 5 below covers exactly what to redo and why.
2

SSH in as root and run the setup script

This one script does everything: installs Node.js 22, PM2, Nginx, and Certbot; clones the app to /ERP; installs dependencies; generates a fresh DATA_ENCRYPTION_KEY; builds the app; starts it under PM2 (auto-restarts on reboot); configures Nginx as a reverse proxy for leadsnextgencentre.online; and opens the firewall.

Partway through, on a fresh install, it will pause and interactively prompt you right there in the terminal for the Super User's name, email, and a password — that becomes the one and only account on the instance (no pre-loaded roster, no shared default password). Right after that it'll also ask you to set the DATA_ENCRYPTION_KEY if one isn't already in .env — press Enter to generate a strong one automatically, or paste your own. On a redeploy of an existing instance both prompts are silently skipped.
ssh root@YOUR_VPS_IP

Download the script and open it to fill in one optional value before running:

curl -fsSL https://raw.githubusercontent.com/Kayo2970/ERP/main/docs/vps-setup.sh -o vps-setup.sh
nano vps-setup.sh

Near the top of the file:

VariableWhat to do
DOMAINAlready set to leadsnextgencentre.online — leave as-is.
CERTBOT_EMAILOptional. Set it to an email address (e.g. "you@example.com") to have the script request your HTTPS certificate automatically at the end. Leave blank to skip and run Certbot yourself in Step 4.

Save and exit (Ctrl+O, Enter, Ctrl+X in nano), then run it:

bash vps-setup.sh

This takes a few minutes — it's doing a full system update, package installs, and a production build. It prints progress as it goes, and ends by printing your new DATA_ENCRYPTION_KEY.

Copy that DATA_ENCRYPTION_KEY value somewhere other than this server the moment it's printed (a password manager is fine). It encrypts every record the app stores — losing it means losing the data with it, backups included. The script never overwrites it on a re-run, so this is the only time you'll see it.
Show the full script contents (also committed at docs/vps-setup.sh in the repo) 
#!/usr/bin/env bash
#
# vps-setup.sh — one-shot bootstrap for the LEADS Dashboard on a fresh
# Ubuntu VPS, run as root, installed to /ERP.
#
# What it does: installs Node.js 22, PM2, Nginx, Certbot and git; clones (or
# updates) the app into /ERP; installs dependencies; generates a fresh
# DATA_ENCRYPTION_KEY the first time it's ever run; builds the app; starts
# it under PM2 with auto-restart on reboot; writes an Nginx reverse-proxy
# config for DOMAIN; opens the firewall for SSH + HTTP/HTTPS; and requests
# a Let's Encrypt certificate if CERTBOT_EMAIL is set.
#
# Safe to re-run: it skips anything already installed/present rather than
# re-doing it, and it never overwrites an existing .env (so it can never
# regenerate — and thereby invalidate — a DATA_ENCRYPTION_KEY that's
# already protecting real data).
#
# Usage:
#   1. Edit DOMAIN (and CERTBOT_EMAIL, optional) below.
#   2. As root: bash vps-setup.sh
#
set -euo pipefail

# ── Configure these two before running ──────────────────────────────────
DOMAIN="leadsnextgencentre.online"
CERTBOT_EMAIL=""   # e.g. "you@example.com" — leave blank to skip HTTPS setup
                    # and run it manually later (see the bottom of this file)
# ──────────────────────────────────────────────────────────────────────────

REPO_URL="https://github.com/Kayo2970/ERP.git"
INSTALL_DIR="/ERP"
APP_DIR="$INSTALL_DIR/leads-dashboard"

if [ "$(id -u)" -ne 0 ]; then
  echo "This script must be run as root (e.g. 'sudo bash vps-setup.sh' or already logged in as root)." >&2
  exit 1
fi

log() { echo -e "\n\033[1;36m==> $1\033[0m"; }

log "Updating system packages"
apt update -y && apt upgrade -y

log "Installing Node.js 22 LTS"
if ! command -v node >/dev/null 2>&1 || [ "$(node -v | cut -d. -f1 | tr -d v)" -lt 22 ]; then
  curl -fsSL https://deb.nodesource.com/setup_22.x | bash -
  apt install -y nodejs
else
  echo "Node.js already installed: $(node -v)"
fi

log "Installing PM2, Nginx, Certbot, git"
command -v pm2 >/dev/null 2>&1 || npm install -g pm2
apt install -y nginx git certbot python3-certbot-nginx ufw

log "Cloning or updating the repository at $INSTALL_DIR"
if [ -d "$INSTALL_DIR/.git" ]; then
  echo "$INSTALL_DIR already exists — pulling latest instead of cloning."
  git -C "$INSTALL_DIR" pull
else
  git clone "$REPO_URL" "$INSTALL_DIR"
fi

cd "$APP_DIR"

log "Installing app dependencies (npm install)"
npm install

log "Configuring environment (.env)"
if [ -f .env ]; then
  echo ".env already exists — leaving it untouched (this is what keeps your DATA_ENCRYPTION_KEY stable across re-runs)."
else
  cp .env.example .env
  GENERATED_KEY="$(openssl rand -hex 32)"
  # .env.example ships without DATA_ENCRYPTION_KEY — add it fresh.
  echo "" >> .env
  echo "DATA_ENCRYPTION_KEY=$GENERATED_KEY" >> .env
  echo "Generated a new DATA_ENCRYPTION_KEY and wrote it to .env."
fi

log "Setting up the Super User account"
# No-op if data/members.json already has accounts in it (e.g. a redeploy of
# an existing instance) — only prompts on a genuinely fresh install.
node scripts/setup-superuser.js

log "Building the app for production"
npm run build

log "Starting the app under PM2"
cat > "$APP_DIR/ecosystem.config.js" <<EOF
module.exports = {
  apps: [
    {
      name: 'leads-dashboard',
      cwd: '$APP_DIR',
      script: 'npm',
      args: 'start -- -p 3000',
      env: { NODE_ENV: 'production' },
    },
  ],
};
EOF

if pm2 describe leads-dashboard >/dev/null 2>&1; then
  pm2 reload leads-dashboard
else
  pm2 start ecosystem.config.js
fi
pm2 save
pm2 startup systemd -u root --hp /root >/tmp/pm2-startup-output.txt 2>&1 || true
# pm2 startup prints a command it wants run once; running as root, it's
# usually applied automatically, but check /tmp/pm2-startup-output.txt if
# the app doesn't come back after a reboot.

log "Writing Nginx config for $DOMAIN"
cat > "/etc/nginx/sites-available/leads-dashboard" <<EOF
server {
    listen 80;
    server_name $DOMAIN www.$DOMAIN;

    client_max_body_size 100M;

    location / {
        proxy_pass http://localhost:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade \$http_upgrade;
        proxy_set_header Connection 'upgrade';
        proxy_set_header Host \$host;
        proxy_set_header X-Real-IP \$remote_addr;
        proxy_set_header X-Forwarded-For \$proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto \$scheme;
        proxy_cache_bypass \$http_upgrade;
    }
}
EOF
ln -sf /etc/nginx/sites-available/leads-dashboard /etc/nginx/sites-enabled/leads-dashboard
rm -f /etc/nginx/sites-enabled/default
nginx -t
systemctl reload nginx
systemctl enable nginx

log "Configuring the firewall"
ufw allow OpenSSH
ufw allow 'Nginx Full'
ufw --force enable

if [ -n "$CERTBOT_EMAIL" ]; then
  log "Requesting a Let's Encrypt certificate for $DOMAIN"
  certbot --nginx -d "$DOMAIN" -d "www.$DOMAIN" -m "$CERTBOT_EMAIL" --agree-tos --non-interactive --redirect
else
  echo -e "\nCERTBOT_EMAIL not set — skipping HTTPS setup. Run this manually once DNS is confirmed pointing here:"
  echo "  certbot --nginx -d $DOMAIN -d www.$DOMAIN"
fi

echo -e "\n\033[1;32m==================================================================\033[0m"
echo -e "\033[1;32mDone. The app is running under PM2 and Nginx is proxying to it.\033[0m"
echo "  App directory:   $APP_DIR"
echo "  Check status:    pm2 status"
echo "  View logs:       pm2 logs leads-dashboard"
if [ -f .env ] && grep -q "^DATA_ENCRYPTION_KEY=" .env; then
  echo ""
  echo -e "\033[1;33mSAVE THIS SOMEWHERE OTHER THAN THIS SERVER — it's the only way to decrypt your data if this disk is ever lost:\033[0m"
  grep "^DATA_ENCRYPTION_KEY=" .env
fi
echo -e "\033[1;32m==================================================================\033[0m"
3

Confirm it's live

pm2 status
curl -I http://localhost:3000

pm2 status should show leads-dashboard as online, and the curl should return HTTP/1.1 200 OK (or a redirect). Then visit http://leadsnextgencentre.online in a browser — you should land on the sign-in screen.

4

Enable HTTPS skip if you set CERTBOT_EMAIL in Step 2

If you left CERTBOT_EMAIL blank, run this once DNS is confirmed pointing at this VPS (ping leadsnextgencentre.online should resolve to this box's IP):

certbot --nginx -d leadsnextgencentre.online -d www.leadsnextgencentre.online

Certbot asks for an email (for renewal/expiry notices) and offers to redirect all HTTP traffic to HTTPS automatically — accept that. It installs its own renewal timer, so the certificate renews itself with no cron job needed.

5

First login & re-configuring email

Sign in with the Super User email and password you set interactively during Step 2's node scripts/setup-superuser.js prompt — a fresh install starts with that one account and nothing else; everyone else is added afterward from Members Directory.

Go to Dashboard → Email Management and redo the SMTP setup — this is the one thing genuinely lost by the reformat, since it lived in the app's own (now-wiped) database, not in DNS. You have two options:

If you still have the old DKIM private keyIf you don't
Paste the exact same key back into the DKIM Signing fields (Domain leadsnextgencentre.online, Selector leads). The existing leads._domainkey DNS TXT record at Hostinger already matches it — nothing to change in DNS. Generate a brand-new keypair (commands below), then update the leads._domainkey TXT record at Hostinger to match the new public key — the old DNS record won't validate a new private key. 
openssl genrsa -out dkim-private.pem 2048
openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in dkim-private.pem -out dkim-private-pkcs8.pem
openssl rsa -in dkim-private.pem -pubout -outform PEM -out dkim-public.pem

The full field-by-field walkthrough (HELO Hostname, Sender Email, DKIM Domain/Selector/Private Key, where each one goes in the dashboard UI, and how to test it) is already written up in docs/direct-send-setup-guide.html in this repo — Steps 4–7 there are exactly what to redo now.

Test with Test Connection & Send Email in the dashboard before considering this done — send to a Gmail address you personally control first.
6

Redeploying updates later

cd /ERP/leads-dashboard
git pull origin main
npm install
npm run build
pm2 restart leads-dashboard

pm2 restart is a brief interruption (a few seconds), not a full outage. Nginx and your SSL certificate are untouched by any of this.

7

Backups

Use Dashboard → Backup to download a full encrypted snapshot regularly and store copies off this VPS. At the filesystem level, everything that matters lives at:

/ERP/leads-dashboard/data/

This holds every collection as encrypted per-collection JSON files, plus data/uploads/ — the real design files, receipts, and visiting cards those records point to. Back the two up together.

None of it is recoverable without the DATA_ENCRYPTION_KEY from Step 2. A filesystem backup of data/ without that key saved somewhere else is just an encrypted blob forever.
8

Troubleshooting cheat-sheet

SymptomCheck
Site doesn't load at allsystemctl status nginx · nginx -t · ufw status
Nginx loads but shows an error pagepm2 status — is leads-dashboard actually online? · curl -I http://localhost:3000 from the VPS itself
App crashed or won't startpm2 logs leads-dashboard --lines 100 — this shows the real Node.js error
Changes not showing after a deployConfirm npm run build finished with no errors before pm2 restart, and that you're in /ERP/leads-dashboard, not /ERP
HTTPS certificate errorscertbot certificates to check expiry · certbot renew --dry-run to test renewal
Outbound mail not sending (Direct Send)Outbound TCP port 25 is blocked by many hosting providers by default — see docs/direct-send-setup-guide.html, Step 1
Server rebooted and app didn't come backRun pm2 startup systemd -u root --hp /root and execute the command it prints, then pm2 save again

Useful commands to keep handy:

pm2 status
pm2 logs leads-dashboard
pm2 restart leads-dashboard
systemctl status nginx
tail -f /var/log/nginx/error.log
