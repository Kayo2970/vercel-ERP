Delete every existing DNS record (except NS/SOA)

Go to hPanel → Domains → leadsnextgencentre.online → DNS/Nameservers → DNS Zone Editor. Click the trash icon on every row except the two NS rows (aster.dns-parking.com, helios.dns-parking.com) and the SOA record if one is shown separately.

3

Fix the PTR (reverse-DNS) record not in the DNS Zone Editor

This one lives at the VPS/network level, not in the domain's DNS zone. Go to hPanel → VPS → your VPS → Network settings / rDNS and set the PTR for 187.52.121.165 to mail.leadsnextgencentre.online.

If you don't see that option, open a Hostinger support chat and ask directly: "Please set the PTR record for 187.52.121.165 to mail.leadsnextgencentre.online."

Don't skip this. It's still wrong right now (currently srv1915749.hstgr.cloud) and is one of the most common reasons big providers reject mail outright, independent of SPF/DKIM being correct.
4

Wait for propagation, then verify each record is live

Give it 15–30 minutes (the TXT records have a 4-hour TTL, but changes are usually visible well before that expires). Check from your VPS or any terminal — these query Google's public DNS directly, bypassing any local cache:

curl -s "https://dns.google/resolve?name=leadsnextgencentre.online&type=TXT"
curl -s "https://dns.google/resolve?name=leads._domainkey.leadsnextgencentre.online&type=TXT"
curl -s "https://dns.google/resolve?name=_dmarc.leadsnextgencentre.online&type=TXT"
curl -s "https://dns.google/resolve?name=leadsnextgencentre.online&type=AAAA"
curl -s "https://dns.google/resolve?name=leadsnextgencentre.online&type=MX"

For the first command, confirm the Answer array has exactly one entry and it starts with v=spf1. For the DKIM one, confirm the key matches what you pasted (compare the first ~30 characters). For AAAA, confirm it returns 2a02:4780:5e:a87a::1.

Check the PTR fix separately:

host 187.52.121.165

Should return mail.leadsnextgencentre.online, not srv1915749.hstgr.cloud.

6

Test send, and how to read the result

In the same screen's Connection Diagnostics & Test panel, put in a Gmail address you personally control (Gmail is the strictest of the major providers — if it passes there, everything else is very likely fine too), then click Test Connection & Send Email.

  • Success message with no bounce — check the actual inbox (and spam folder) a minute or two later. The dashboard confirming "sent" only means the SMTP handoff worked, not that it landed in the inbox.
  • Still bounces with an SPF/DKIM authentication error — DNS likely hasn't propagated yet everywhere. Re-run the verification commands from Step 4; if they show correct values, wait longer and retry the test send.
  • Bounces with a different error — copy the exact bounce text; it usually names the specific problem directly (rejected recipient, connection refused, etc).
7

What's left after all of this

Once a test send to Gmail lands cleanly in the inbox, the technical setup is done. Two things worth knowing beyond that:

  • Sending reputation takes a little time to build. This domain/IP combination is effectively starting fresh after the reformat and DNS reset — even with everything configured correctly, the first handful of emails from a "new" sending identity can occasionally land in spam at some providers until they've seen enough legitimate volume to trust it. This isn't a misconfiguration; it resolves itself with normal use over the next several days.
  • BIMI (the sender logo) won't visually show up yet, even though the DNS record is in place — it only activates once DMARC is enforced at p=quarantine or p=reject, and yours is intentionally p=none (monitor-only) for now. Tightening that is a separate, deliberate decision to make later once you've confirmed mail authenticates cleanly for a while — don't rush it, since a misconfigured enforced DMARC can cause your own legitimate mail to get rejected.
