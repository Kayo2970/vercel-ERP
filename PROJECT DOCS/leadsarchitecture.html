How every module actually moves data

★

Module integration map

One diagram, every cross-module dependency in the codebase. Members is the hub — every other module resolves a person through it — and three narrower chains run through it: Events → Tasks → Ratings feed each other directly, while Reports and the Audit Log are pure sinks that never write back.

★

ER diagram

There is no database engine here — data/database.json is nine plain arrays in one file (§01). Nothing below is enforced by a schema: no foreign-key constraints, no cascade deletes, no uniqueness beyond what an individual API route hand-checks (email on Members, slug on Forms). This diagram is the shape the application imposes on that JSON in practice, not a guarantee the file actually upholds.

01

System overview

One Next.js process serves every browser. There is no separate database server: data/database.json on that process's own disk is the database, guarded by a single in-memory write queue.

02

The sync mechanism

No websocket, no push. Every open tab polls GET /api/data every 7 seconds and re-renders if anything changed. Every module below rides on this same path.

03

Login & session

No password hashing, no token — a member row and a client-side localStorage flag is the session.

04

Tasks

follows sync path

A status lifecycle with one branch (extension requests need leadership sign-off) and a visibility rule that depends on whether the assignee is a person or a whole committee.

05

Events

follows sync path

Two screens: the events list (plain CRUD) and the per-event workspace, where committees and tasks nest inside one event record.

06

Ratings

follows sync path

One evaluation writes two records: the rating itself, and a score stamped back onto the source task.

07

Reimbursements

follows sync path

The only module with two distinct human reviewers on one record, and a stage that's derived from who's acting — not from which button they clicked.

08

Announcements

follows sync path

Plain CRUD, plus a self-contained "dispatch" step that looks like it sends email and deliberately doesn't.

09

Forms & public submissions

follows sync path

The only module with an unauthenticated write path — anyone holding the link can create a real record without logging in.

10

Directory

CSV import skips the server

The identity table every other module's assigneeId / targetId / memberEmail resolves back to. Most of it follows the standard pattern — bulk CSV import doesn't.

Sync gap found while mapping this Bulk CSV import builds each new member in memory and finishes with one saveMembers(currentMembers) call — which only writes localStorage. Unlike addMember() (used by the single-add form), it never calls serverPost. Imported rows are visible instantly to the person who ran the import, then vanish for them too on their next poll, and never appear for anyone else — the same failure mode as the reimbursement ghost-revert bug, on a path that was never patched.
11

Reports

read-only

A pure aggregation view — it holds no state of its own, so it's never the source of a stale-data report, only ever a symptom.

12

Settings

writes never reach the server

Three tabs — Account, Roles & Permissions, Audit Log. Only Account has a write path, and it's the second module found to skip local-data.ts entirely.

Sync gap found while mapping this Renaming yourself or setting a password in Settings only ever changes this browser's copy of your member record — it never reaches data/database.json. The next 7-second poll on this same device overwrites it right back to the server's version, so the change doesn't even survive locally. This is separate from — and on top of — the fact that "change password" doesn't hash or verify anything real (see docs/bugs-to-fix.md item 6).
13

Access tiers

Seven numeric tiers, lower number = broader access. Tiers gate what's visible and actionable inside a module — they don't gate which modules appear in the sidebar.

TIER 1

Super User

Full operations & settings control. Only tier that can't be bulk-deleted from Directory.

TIER 2

Centre Head

Member management, final reimbursement sign-off.

TIER 3

Head of Events

Event creation, task assignment, final reimbursement sign-off.

TIER 4

Advisory Board

Strategic read-only oversight — sees everything, assigned nothing operational.

TIER 5

Core Committee

Runs day-to-day operations; first-pass reimbursement reviewer; only non-leadership tier that can build public forms.

TIER 6

Training Associate

Completes assigned tasks, submits own claims.

TIER 7

Alumni

Mentorship / advisory division — outside the active operational chain.
